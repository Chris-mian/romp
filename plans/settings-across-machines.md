# Settings across machines: local precedence, per-machine pins, and proposals instead of silent adoption

**Status:** a design read by the manager on 2026-09-18 (written that day by the metrics worker on the manager's dispatch; the user's rules of 2026-09-18, paraphrased below). Phase one is split (the manager, 2026-09-18, on the user's ask that this move now): phase one A, every kernel-side rule and the gear surface, is being built; phase one B, the owner-less notice card with its three actions, follows pull request 1831 and the notice action-kind API (both merged 2026-09-19; one A merged as pull request 1859; one B's design is the last section of this document).

## The ask

The user connected a new machine whose task tracking switch was off, and their own machine's task tracking turned off too: the Outline and Feed panes vanished from the dashboard they were working in, with no word from romp about why. The newly attached machine's value had won, because the four kernel-side settings that converge across attached machines converge by the newest gesture stamp, and the new machine's stamp was newer.

The user's three rules (paraphrased):

1. **The local machine's setting takes precedence** when two machines connect. A value held by a remote machine never silently applies to this kernel.
2. **Settings are synchronized by default, but every one may differ per machine.** A per-machine pin the user can set from the UI, with the synchronized value and the pinned value both visible.
3. **A pop-up alerts the user before a remote change applies**: which machine, which setting, from what to what, with Apply and Keep mine as the answers, and Keep mine on this machine as the pin. Never a silent flip. A proposal that is not answered applies nothing.

This document turns the three rules into a model, checks the current code it replaces, and lays out the protocol, the stores, the UI, the migration, the tests and the phases.

## The premise, checked in code

**Four stores converge by the newest stamp.** `_MESH_ADOPTED_SETTINGS` in kernel/kernel.py names them: `compactSuggest` and `autoNudge` (both in the auto-nudge blob, `auto-nudge.json`, under `compactSuggestGt` and `gt`), `fileEditing` (`file-editing.json`) and `taskTracking` (`task-tracking.json`). `_mesh_settings_snapshot` reads each store once and returns its value and its stamp together (one snapshot, so a click landing between two reads cannot hand a peer an old value under a new stamp); `/version` serves both under `settings` and `settingsGt`.

**The polling peer adopts.** The tunnel supervisor polls every attached host's `/version` and hands the answer to `_converge_peer_settings`, which runs two legs, both gated on the peer's trust (an isolated peer is neither read nor written): `_adopt_peer_settings` applies every adopted store whose peer stamp is NEWER than the local store's last-applied stamp, through the setting's own gt-gated setter, under the PEER's stamp (a same value under a newer stamp is adopted too, for its stamp); `_older_peer_settings` and `_push_settings_to_peer` hand the peer our value where OUR stamp is newer, through the peer's `POST /mesh-settings`, whose `_apply_mesh_settings` runs the same setters. Latest wins in both directions of a one-way poll, and this is exactly the road the user's task tracking took: the new machine's stamp was newer, the local kernel adopted off, and the panes it drives vanished.

**The stamps are gesture times in epoch milliseconds, minted on the device.** `_gesture_ms` reads them; the gear's gesture clock lifts each new stamp above the highest stamp the page has seen for that store, so a slow clock still outranks what it knows of. Three rules order applies (`_setting_stale`, `_gesture_echo`, and the setters' read-check-write under `_SETTINGS_LOCK`): a stamp at or below the applied stamp stands down, loudly, with a `settingStale` frame to the delivering socket; an EQUAL stamp carrying the SAME value is the gesture's own echo and is quiet; an equal stamp carrying a different value stands down (determinism under identical clocks). The equal-stamp rule is what the adoption relies on to stop ping-pong: after an adoption the two machines hold the same stamp, and an equal stamp is never adopted.

**The browser broadcasts clicks too.** federation.ts's `KERNEL_SETTING` set sends a gear click for these settings (and the judge-tier settings) to the local kernel and to every attached host, queued per host while a socket is down and flushed on reconnect with the original stamp. So a remote value reaches a kernel by two roads: the user's own click in a dashboard attached to it (immediate, stamped by that click) and the supervisor's poll (a peer's stored value under a newer stamp). The user's first rule speaks of the second road; the second rule (a per-machine pin) has to hold against the first road as well, or a click on one machine's gear still flips a pinned machine.

**The gear shows divergence as a mixed mark.** Every kernel-side row in gear.js carries an `rs-mixed` span; `fill()` reads every attached host's `/version` and marks a row whose values differ across hosts. The gear already knows the host list, so it has a place for a per-machine pin without new plumbing.

**Where a kernel can tell the user something.** Two vocabularies exist. The gear's `settingStale` toast (`rs-stale-toast`, gear.js) is a kernel-to-dashboard message about a refused gesture, with an "Apply anyway" action, shown inside the settings modal to the socket that made the gesture. The notice producer (`post_notice`, kernel.py; plans/notice-cards.md, shipped since 2026-09-16) posts a feed card for a session with up to four action buttons whose routes come from an allowlist (`NOTICE_ACTION_ROUTES`, today `/send` only), marked `needsYou` when the human is the bottleneck, expiring on a stamp, revised under one key; the feed executes an action through the kernel (`noticeAction`, answered by `noticeActionDone`).

**Per-browser settings are a separate class.** settings.ts's `RompSettings` (`romp:settings` in localStorage) holds this browser's display preferences: `compact`, `colormap`, `subgoals`, `showIndexJudges`, `showTriageJudges`, `backend`, `defaultDir`, `showBranch`, `showSessionBadge`, `tabCtx`, `stripGroupRows`, `showFilesControl`, `chatScheme`, `theme` (and the derived `chatTabTheme`), `panes`, `denseChrome`, `tabWidgets`, `statusWidgets`, `tabsLocked`. They travel between this browser's same-origin views and, through `installSettingsSync`, between the panes one dashboard hosts; they never cross a kernel. Two other kernel-side stores are per-install by design and neither broadcast nor adopted: `thinking-summaries.json` and `whole-chat-frames.json` (each says so in gear.js and in federation.ts's exclusion list); `update-mode.json` broadcasts as a click but is not adopted (a boot policy per install).

## The model

Three facts per synchronized setting per kernel:

- **The local value**, in the store as today, with its applied stamp. This is what this kernel runs on. Nothing but a local gesture (a click in a dashboard attached to this kernel, or an accepted proposal) writes it.
- **The pin**, per store, per kernel: a file `settings-pins.json` under the state root, `{"<store>": {"pinned": true, "gt": <stamp of the gesture that set the pin>}}`. A pinned store keeps its local value against every remote input: a proposal is never raised for it, and a broadcast click from a dashboard attached to another machine stands down on it (the setter answers the delivering socket with a `settingStale` frame whose `why` is `pinned`, so the gear that sent the click sees the mark, never a silent refusal). A click from a dashboard whose LOCAL kernel is this one applies as ever: the pin protects the machine from other machines, not from its own user.
- **The proposal**, at most one per store: a remote value under a newer stamp that this kernel has NOT applied. It lives in `settings-proposals.json` under the state root, `{"<store>": {"host": "<peer>", "value": <bool>, "gt": <peer stamp>, "seen": <epoch s>, "current": <the local value at the time>}}`, and is surfaced to the user; it applies only when the user says Apply.

The synchronized value the second rule wants visible is the newest stamp across the attached hosts, read the way the mixed mark reads today: from every host's `/version`. The gear shows, per row, the local value (the control), and when a pin or a proposal stands, a second line under the row: "Pinned on this machine; the other machines are on" or "TESTHOST proposes off (yours is on)" with the two answers.

## The protocol: from adoption to proposals

**`/version` is unchanged in shape.** It keeps `settings` and `settingsGt` from the one snapshot. It gains one dict, `settingsPinned`, `{"<store>": true}` for every pinned store, so a peer's push leg and the gear's mixed mark can tell a pinned divergence from an unconverged one. Additive, so an older kernel reading it ignores the key and an older kernel serving nothing under it reads as no pins.

**The polling peer proposes, never adopts.** `_converge_peer_settings`'s inbound leg becomes `_propose_peer_settings`: for every adopted store whose peer stamp is newer than the local applied stamp and whose value differs, it writes or refreshes the proposal record (the host, the value, the stamp, the local value at that moment); a peer stamp that is newer but carries the SAME value lifts the local stamp as today (the stamp-only adoption stays, because it applies nothing the user can see and it is what keeps a later local click from being adopted away; the record notes it as `stampOnly`). A proposal for a pinned store is not raised (the pin is the standing answer). When the peer's stamp changes again (the peer's user clicked once more), the record is refreshed to the new value and stamp and the surfaced card is revised (the notice's `rev` moves); when the peer's value comes to equal the local one (the peer adopted ours, or its user clicked back), the record is dropped and the card expires. A proposal that is never answered writes nothing to the local store, ever.

**The outbound leg stands.** `_older_peer_settings` and `_push_settings_to_peer` keep handing a peer our newer value through its `/mesh-settings`; on the peer that route now runs the same proposal rule (`_apply_mesh_settings` writes a proposal record instead of applying, and answers the current snapshot as today). The push exists so a hub that is polled by nobody still learns of the other machine's value; under this design what it learns is a proposal.

**The equal-stamp rule and proposals.** Adoption avoided ping-pong by making both stamps equal after an apply. A proposal applies with the PEER's stamp when accepted (so the two machines hold one stamp and the peer's next poll sees nothing to propose back) and writes nothing when refused. A refusal that is also a pin makes the divergence permanent by design and visible on both `/version`s. A refusal that is not a pin (Keep mine, this once) drops the record and marks the peer stamp as answered in the record file (`answered: {"gt": <stamp>}`), so the same stamp is not proposed again on the next poll; the next click on the other machine, under a newer stamp, raises a fresh proposal. Two machines each proposing to the other (both clicked, different values, neither pinned) each show the other's proposal; whichever user answers Apply first makes the stamps equal and the other proposal expires on its next poll. There is no state in which a store flips without a local answer.

**The setters gain one gate.** Each adopted store's setter (`_set_auto_nudge`, `_set_compact_suggest`, `_set_file_editing`, `_set_task_tracking`) reads the pin before the stale check when the gesture arrives from a dashboard whose local kernel is not this one. The WebSocket arm knows which kernel a dashboard belongs to today only by the socket; the gear's broadcast messages gain a field, `origin: "local" | "remote"`, set by federation.ts (the LOCAL entry in its host list against the others), and a message without the field is treated as remote (the conservative reading for a dashboard from before this change). A remote-origin click on a pinned store answers `settingStale` with `why: "pinned"` and the kept value; the gear's existing stale toast shows it, in the modal's own vocabulary, without a new surface.

## The pin store

`settings-pins.json` under the state root, written by one setter, `_set_setting_pin(store, pinned, gt)`, through `_atomic_write` under `_SETTINGS_LOCK`, gt-gated like every setting (a stale pin gesture stands down; an equal stamp with the same pin state is an echo). Two doors set it: the gear's WebSocket message `setSettingPin {store, pinned, gt}`, always to the LOCAL kernel only (a pin is per machine by definition, so it is not a `KERNEL_SETTING`), and the proposal's "Keep mine on this machine" answer, which sets the pin and drops the proposal in one step. The pin's precedence: above a proposal (none is raised), above a remote-origin click (stands down), below a local-origin click (applies), below nothing else. Unpinning does not apply anything: the next poll may raise a proposal for the current divergence, and the user answers it.

## Where the pop-up lives

The user's word is "pop-ups". Two homes were weighed.

**The gear's modal vocabulary.** The `settingStale` toast already tells a dashboard that a gesture was refused and offers Apply anyway. A proposal could ride the same toast: "TESTHOST turned task tracking off; yours is on. Apply, or Keep mine." It reaches only a dashboard with the settings modal open, on the kernel that holds the proposal, and only while the modal is open, so a proposal raised while the user works in the chat would wait unseen until they next open the gear. That fails the third rule's "before it applies" only in the weak sense (nothing applies), but it fails the user's expectation of being told.

**A notice card through the notice producer.** `post_notice` gives a proposal a feed card with the producer label `settings`, a key `proposal.<store>`, a title in the user's terms ("Task tracking: TESTHOST proposes off, this machine is on"), three actions, Apply, Keep mine and Keep mine and pin this machine, `needsYou` true, revised under its key when the peer's stamp moves, expired when the record drops. The card is a decision only the user can make, which is exactly the interrupt-only-when-the-human-is-the-bottleneck rule: a machine's setting is about to differ from another's and romp cannot know which the user wants. The card belongs to no session. It takes the OWNER-LESS notice road that pull request 1831 adds (the manager's ruling of 2026-09-18): the settings producer posts from inside the kernel with an EMPTY sid, the reserved owner-less home whose Notes run is drawn first in the feed. Never a stand-in session (a misattributed card breaks the model) and never a second reserved owner (one owner-less home; a distinct run title for machine proposals can come later from the boards' data door, as a board or a category of its own).

**The decision: the notice card, with the gear's toast as the second surface.** The card is the pop-up the user asked for: it appears where they are working, it is a needs-you decision, and its two answers are the two the rules name. The gear shows the same proposal under the affected row when the modal is open (the second line described in the model), with the same two answers, so a user who opens the settings to look sees the pending proposal beside the control and never a control that silently disagrees with another machine. Answering in either place clears both.

**The action routes.** The three actions are of the new ACTION KIND the cards worker is adding to the notice producer for held mail (an action kind names its route and its body shape, and the allowlist admits kinds rather than bare routes), against one new route, `/setting-proposal`, with the argument the allowlist demands: the route acts only on this kernel's own proposal records, keyed by store and stamp (`{"store", "gt", "answer": "apply" | "keep" | "pin"}`), it applies a value only through the store's own gt-gated setter under the peer's stamp, and it names no session, no text and no target, so a producer cannot route the user's click anywhere but the proposal it posted. A body whose `gt` no longer matches the record (the peer moved on) is refused with the reason and the card is revised. Phase one therefore depends on two changes landing first: pull request 1831 (the owner-less notice home) and the action-kind API; it says so in its body and is cut after both merge.

## Migration

Today's converged values stay as they are: no store is rewritten, no stamp moves, no pin is created. On the first boot with this design, the poll's inbound leg raises a proposal only where a peer holds a NEWER stamp with a DIFFERENT value than the local store; two machines that converged yesterday hold equal stamps and raise nothing. The pins file and the proposals file are absent until the first pin or the first proposal. An older peer (no `settingsPinned` in its `/version`, an `/mesh-settings` that applies) is read as unpinned and told nothing new: our push still reaches its route, and its kernel still adopts our value, so a mixed mesh converges one way (the older kernel toward the newer) until both update; the reference says so.

## Tests

- **The proposal, not the apply.** The hermetic pair in tests/test_mesh_settings_adopt.py (two state roots, one module, a peer as its `/version` dict through the REAL poll): a peer with a newer stamp and a different value leaves the local store byte-for-byte unchanged and writes one proposal record with the host, the value, the stamp and the local value; a same value under a newer stamp lifts the stamp and no record; an equal stamp writes nothing (the base's test, restated).
- **The answers.** Apply writes the value under the peer's stamp through the setter and drops the record; Keep drops the record and marks the stamp answered, so the next poll with the same stamp raises nothing and a newer stamp raises a fresh one; Pin sets the pin, drops the record, and the next poll with a newer stamp raises nothing.
- **The pin against a click.** A `setTaskTracking` with `origin: "remote"` on a pinned store answers `settingStale` with `why: "pinned"` and writes nothing; with `origin: "local"` it applies; without the field it is remote.
- **The card.** `post_notice` with the empty sid (the owner-less home of pull request 1831), the `settings` producer, the key, the three actions of the new kind against `/setting-proposal`; the revision when the stamp moves; the expiry when the record drops; the route's refusal on a stale `gt`; the feed drawing the card in the Notes run first.
- **The equal-stamp freeze does not return.** Two kernels each holding a proposal from the other; one Apply makes the stamps equal and the other record drops on its poll.
- **The gear.** A served test over a hermetic pair reads the second line under the row for a pinned store and for a proposed one, and the mixed mark's coexistence with `settingsPinned`.
- **Red first at main for each**, executed at the base: the adoption test's own assertion that the local store CHANGED is the base's behaviour and turns red under the proposal rule, which is the one test this design deliberately inverts.

## Roads not taken

- **Local always wins, no proposal.** Meets rule one and leaves the machines silently different, which is the state the mixed mark was built to end; the user's rule two says synchronized by default.
- **A vector of per-machine values in one store.** Every machine holding every other machine's value would make the pin a query rather than a fact, and a machine attached for the first time would have to learn the whole vector before it could show one control.
- **The pin as a wall-clock lease.** A lease that expires is a time heuristic; the pin is an event the user set and the user clears.
- **Proposals in the gear toast alone.** Reaches only an open modal; the user asked to be told.
- **A modal dialog over the dashboard.** The panels rule (ui/CLAUDE.md) puts decisions in centered modals over the unchanged dashboard, but a decision that arrives while the user types in a chat must not steal focus; the card waits where the user looks next, and the gear's line waits where the setting lives.

## Phase one B: the card, and how the owner-less rule meets the kind table (2026-09-19)

**The contradiction, read in code.** This document says the proposal card takes the OWNER-LESS notice road (an empty sid, the reserved home, the Notes run first) and carries three actions. The notice-cards plan's kind table says the owner-less home takes NO actions, and the kernel enforces it twice: `post_notice` refuses actions on the owner-less road ("an owner-less card has no session to send to: actions need a session") and `_notice_action_run` refuses a hand-made owner-less id ("an owner-less card has no actions"). Both refusals exist for the two kinds the table holds today: `send` delivers text to the card's OWN session and `quarantine` decides a message held FOR the card's owner, so each needs an owner and an owner-less card could route a click nowhere honest. The settings kind is different in the one way that matters: `setting-proposal` names no session, no text and no target. It acts on THIS kernel's own proposal record, keyed by store, machine and stamp, through `/setting-proposal`'s own checks, and the same click from any dashboard does the same thing. There is nothing an owner would add.

**The resolution: the kind table says whether a kind needs an owner; the owner-less refusals key on that fact, not on the home.** Each entry of the kind table carries `owner: True | False`. `send` and `quarantine` keep `True`, and both refusals above stand for them, word for word. `setting-proposal` carries `False`: `post_notice` admits its actions on the owner-less road, and `_notice_action_run` runs an owner-less id whose stored action is of an owner-less kind (the exact match by kind and body still stands, so a hand-made id runs only an action the kernel stored). The rule the notice-cards plan states ("the owner-less home takes no actions") is restated there as "takes no action that needs an owner", which is what its two kinds meant. Not taken: a reserved kernel-owned producer sid (this document's own model rules out a second reserved owner, and a card wearing a session's name for a machine's decision is the misattribution the model forbids); a stand-in session (the same); an unconditional relaxation (a `send` on the owner-less home has nowhere to send).

**The kind is the kernel's alone.** A `setting-proposal` action is posted only from inside the kernel (the poll leg and the push receiver, through `post_notice` with `internal=True`, a keyword the route and the command never set); the route and `romp card` are refused the kind by name ("that kind is posted by the kernel alone"). A producer outside the kernel could otherwise put a label on a button whose body answers a pending proposal the other way, and the click's checks would let it through because the body would be valid. The runner, `_notice_run_setting_proposal`, hands the stored body to `_answer_setting_proposal` unchanged (`{store, host, gt, answer}` with `answer` in `apply | keep | pin`; no click input), so every guard of the route (the store known, the machine's record present, the stamp current, a local click that outranks the record refused and dropped, the pin taken from the local origin) holds on the card exactly as in the gear, and the answer's words are the route's.

**The card's life follows the record.** One card per (store, machine) record, the key `proposal.<store>.<machine>` (the machine's row key, which is a safe id; the key stays inside the key grammar's 64 characters by truncating the machine's part), the producer `settings`, `needsYou` true, `dismissOnAction` true, the title "Task tracking: TESTHOST proposes off; this machine is on", the body naming the two values and that the gear shows the same line, the three actions Apply, Keep mine, Keep mine and pin this machine. It posts when the record is raised, posts again (a new revision under the same key) when the record is refreshed by a moved stamp, and expires (`expire_notice` on the owner-less home) when the record drops for any reason: an answer from the card or the gear, the values coming to agree, a local click that outranks it, a pin, a re-key onto the row key (the self-name key's card expires, the row key's posts), a detached row. A card the user clears without answering leaves the record standing: the gear's line still shows it and the poll finds it standing, so nothing posts again until the stamp moves. The sync notice that was the interim alert retires: two alerts for one event is noise, and the card is the one the user asked for.

**Tests for one B.** The kind table: `setting-proposal` accepted at the post with a valid body and refused by name for a body outside its shape or an answer outside the three; refused at the post from the route and the command; admitted on the owner-less road while `send` on the owner-less road is still refused. The runner: a click on the card applies under the peer's stamp and the card and the record are gone; Keep drops the record, the card expires and the same stamp raises no card; a stale stamp is refused with the route's words and the next poll posts the refreshed card; the gear's answer expires the card. The life: one card per machine when two machines propose one store; the re-key expires the self-name card and posts the row key's; a detached row's card expires. The feed: a served lab over a hermetic pair draws the card first in the Notes run with the three buttons, and Apply from the card changes the control in the gear. Red first at the base for each, executed.

## Phase two, re-drawn: a machine selector above the tabs, the disagreement flag, and the pin as a scoped value (2026-09-19)

**The ask (the user, 2026-09-19, through the manager; paraphrased).** With more than one kernel connected, the settings card gets a MACHINE SELECTOR at its very top, above the tabs: a dropdown that reads "All kernels" by default and lets the user pick one or several kernels, so that specific settings can be applied to those alone. And whenever the kernels disagree on a setting, the disagreement is FLAGGED so it is seen without opening a section.

**How this meets the model of one A.** The three facts per store per kernel stand (the local value, the pin, the proposal). The selector is a VIEW over them, and a scoped change is what the pin was always for:

- **"All kernels" is the synchronized view**, and the card as it is today. Every control shows this kernel's value; a click broadcasts to every attached kernel as the gear's broadcast does (federation.ts's `KERNEL_SETTING` fan-out, each copy stamped with its origin), and each machine's pin gate answers as in one A: a pinned store stands the remote copy down and the toast says so. A row whose kernels DISAGREE wears the flag: the `rs-mixed` mark the gear already computes from the `/tunnels` rows, made unmistakable as a badge on the row (the word "differs" in the warning tone, not the quiet grey mark), and the selector itself carries a COUNT of the rows that differ, so the disagreement is seen from the top of the card before any tab is opened. The flag names the machines and their values on hover (the mark's title today names the hosts; it gains each host's value).
- **Picking one kernel scopes every control to THAT kernel's values.** For a remote kernel the values are its `/version` as the `/tunnels` row carries it (`settings`, `settingsGt`, `settingsPinned`, the same read the mixed mark makes); for this kernel, the local snapshot. A change made under that scope applies to it alone and PINS the store there: a per-machine value that differs from the synchronized one IS a pin, so the gate that keeps the machine's value against the mesh is the state the user just asked for. The pin glyph of the old phase-two text becomes the mark of that state on the row: a small pin at the row's right edge, lit while the store is pinned on the scoped kernel, its hover naming the synchronized value beside the pinned one ("pinned off here; the other machines are on"). Un-pinning (a click on the lit glyph) clears the pin and returns the row to the synchronized value: the kernel takes the newest stamp across the attached hosts through the store's own setter, the same value the mesh would have proposed. Picking several kernels applies to each of them the same way, one message per kernel.
- **How the scoped intent rides the message.** The gear's broadcast copies carry `origin` (local to this dashboard's kernel, remote to every attached host). A scoped change to a remote kernel is a remote-origin click there, which its pin gate would stand down; the user explicitly scoped to it, so the message carries `scope: "pinned"` beside `origin`, and `_pinned_stand_down` honours it: a remote-origin gesture WITH the scope applies and sets the pin under the gesture's stamp (the pin store's own gt gate applies, so an older scoped gesture still stands down); a remote-origin gesture WITHOUT it stands down on a pinned store as in one A; a local-origin gesture applies as ever and never pins on its own. Un-pinning rides `setSettingPin {pinned: false}` addressed to the one kernel, stamped by federation with the origin that kernel sees and the same scope, so the arm accepts the explicit un-pin from a dashboard on another machine; without the scope the arm keeps its local-origin rule. The scope is never set by a broadcast: only a selector pick produces it, so nothing in a mixed mesh changes for kernels that never see the selector.
