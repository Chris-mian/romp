# Tab state badge (design note)

Status: CONFIRMED by the user (2026-09-21). The earlier stacked model is replaced by the model below: only Needs you is a top-right dot, retrying moves to the left status dot under badge mode, Blocked is unchanged. Code follows.

The badge is a top-right MAGENTA dot for Needs you, and nothing else. On seeing the stack mockups the user separated the three ring states by kind (2026-09-21): retrying is not an attention state, it is an alternative to working, so it belongs on the LEFT status dot (amber), not a top-right badge; Blocked is a hard run-state stop that outranks working or anything else and keeps its red dashed ring and red fill as today; only Needs you, which can ride any run state, gets the top-right dot. So there is no stack and no precedence among badges: at most one dot (Needs you) sits at the top right. The setting changes two shapes, the Needs-you cue (ring to top-right dot) and the retrying cue (ring to left amber dot); working, idle and Blocked are untouched. Default OFF; the dashed ring stays available.

## Why

The user asked (2026-09-21) for a switchable experiment: show a session's state as a small dot rather than the dashed outline ring, to see whether it reads better. The first model put a dot per state at the top right, stacked. After the mockups the user refined it: only Needs you is a top-right dot; retrying is a run state and moves to the left dot; Blocked keeps the ring. This note is that refined model.

This note does not reopen the ring renames or the state tokens; those are the user's decisions, recorded in plans/needs-you.md.

## The states today (the premise, read in code)

Two places show a tab's state today: the dashed outline RING and the left STATUS DOT.

The RING is one of three, chosen by a widget registry since 2026-09-14; the class names are not literal:
- `ring-needs-you` is the RED "Blocked" ring (a live prompt or an on-you API stop), `ui/webview/styles.css:593`, drawn from `--state`.
- `ring-waiting-on-you` is the MAGENTA "Needs you" ring (a filed needs-you card), `ui/webview/styles.css:601`, from `--st-needs-bg`.
- `ring-retrying` is the AMBER "Retrying" ring, `ui/webview/styles.css:593` (shares the red rule, reads `--state` from `.tab-retrying`).
A ring is an `outline` inset by `outline-offset: -2px`, so it takes no layout space. `tabRingId` picks the first of `RING_ORDER` whose switch is on and predicate (`RING_TEST`) holds; `composeTabRing` puts on exactly that one; `applyTabStatus` (called from three sites: renderTabs, the skeleton tab and the loading tab) calls it per tab per paint. Tokens: `--st-needs-bg #d946ef` (light `#a21caf`), `--st-retrying-bg #e67e22` (light `#9C4A0C`), `--st-blocked-bg #e5484d`, `--st-awaiting-bg #c0392b`.

The left STATUS DOT is `.tab-dot`, classed by `tabDotClass`: working is `.tab-dot` (gold, `--st-working-bg`), awaitingBg is `.tab-dot await` (green, `--st-awaitbg-bg`), opening is `.tab-dot opening`, an unknown state is `.tab-dot unknown` (a grey ring), COMPACTING is null (the compacting bar takes the slot, not a dot), and EVERYTHING ELSE, including retrying and blocked, is `.tab-dot none` (hidden); the dot widget's "Grey dot when idle" option instead renders every `.tab-dot none` state as `.tab-dot idle`, a quiet grey dot, so this note (and the "Blocked keeps its red dashed ring" paragraph and test 3 below, Blocked unchanged) describe the DEFAULT hide-when-idle option, and the grey option is why the shipped re-ink drops both `none` and `idle` before adding the amber `retrying` (a leftover `idle` would dim it; PR 2023). So today the left dot shows working and awaiting only; retrying shows as the amber ring and blocked as the red ring plus fill, neither colouring the dot. The dot is composed by the before-side compose call in render.ts (the "before" widget). The mobile switcher's leading dot maps the same: `#mcur .wd` and `.mrow .workdot` are gold (`--st-working-bg`), `.await` green (`--st-awaitbg-bg`); needs-you shows there as `#mcur.ask`'s dashed magenta border and `.mrow.ask`'s magenta left bar (both in the kernel's mobile CSS strings, cited by selector: the line numbers drift).

## The Needs-you dot

The badge is one magenta dot at the tab's top-right corner, shown only when the tab is in the Needs-you state (`RING_TEST["ring-waiting-on-you"]`: `status.needsYou === true` and the tab is not closed).

**Shape and place.** An EMPTY dot is 8px across; carrying a count it is a 14px pill (`min-width: 14px`), a two-digit count widening it (the "12" pill about 16px) and "99+" past 99, and under dense chrome a 12px pill tucked to `top: 1px; right: 1px`. `border-radius: 50%` (the bare dot) or `7px` (the pill), `position: absolute` on `.tab`, `top: 2px; right: 2px` so it clears the tab's 6px top corner radius (`styles.css:529`) and sits fully inside the border box. `.tab` is already `position: relative` (`styles.css:525`), so the dot joins no flex flow: the tab's size does not change and the status dot, label, host prefix, context gauge, hot-key keycap and close all keep their places. It draws on top (z above the fill and any inset outline) with `pointer-events: none`.

**Contained.** The dot stays within the border box, never above the top edge, so `#tabbar`'s horizontal clip (`styles.css:401`) cannot cut it; the tab sets no `overflow` (`styles.css:523`), so it does not clip the dot. Active, inactive and peek tabs place it identically (a peek is a normal-size tab, `styles.css:591`); only the contrast floor differs by ground (below). The dot is at the right; the loading swirl rides the left dot slot (the `.tab-dot.loading` rule), so the two never meet. The close glyph, which a wide pill can reach, paints ABOVE the pill (z-index 4 over the pill's 3) on hover and on the active tab, so the x stays clickable over a "99+"; the hot-key keycap keeps its place.

**One top-right dot, no stack; it carries the count.** Needs you is the only top-right dot, so there is never more than one at the top right. It carries how many things need you in the session (see the count below): preferred as a number in the dot (black on the dark magenta, the state's foreground token on the light; see the count section), with a capped series of dots as the fallback.

## The count in the Needs-you dot

The Needs-you dot carries the count of things that need you in the session (the user, 2026-09-21). CHOSEN from the mockups by the manager on the user's delegation (2026-09-21 evening PT): the NUMBERED DOT. The choice is fixed for all tabs (the dot's pixels are the same on every tab), not a per-tab switch.

- The numbered dot (chosen): a number in the dot. The dot is sized for the digits; a two-digit count widens it into a short pill; it stays contained at the top-right and moves nothing. The digit is black on the dark-theme magenta (`#d946ef`); on the lighter light-theme magenta (`#a21caf`) black is only 3.32:1, under the 4.5:1 text floor, so the digit there inks in the state's own foreground token `--st-needs-fg` (white, ~6.32:1). A count of one shows "1", not a bare dot. Past 99 the dot shows "99+".
- The capped series (the road not taken, kept for the record): a series of dots, one per Needs-you item, in the horizontal top-aligned row (each half a dot to the left of the one before it, the most recent at the corner), capped at FOUR. Five or more items still show exactly four dots, with no plus and no overflow marker; the fourth dot stands for "four or more".

Source, in code, so the readings never disagree: the count is `needsYouCount`, an ADDITIVE wire field beside the `needsYou` boolean, computed where the boolean is (the kernel's per-session read in build_session, tallying `_card_needs_you` per sid, the SAME one rule the membership set (needsYou) and the feed's Needs-you COLUMN read). The Needs-you box HEADER counts the rows it shows: the goal rows (`_needs_you_rows`, dropping hard stops and provisional cards) plus the needs-you notice rows `_chat_notices` appends, so it keeps notices and is smaller than the column only by hard stops and provisional cards; it is a different tally, not this one. The app-icon badge count skips provisional cards, a third tally. An older page without the field shows a bare dot from the boolean; a newer page shows the count. The digit-ink contrast pin PARSES the sheet (the base rule's color and the `body.theme-light` override, the hex expanded, the light ink resolved by cascade) and asserts 4.5:1 in both themes: black on the dark magenta, `--st-needs-fg` (white) on the light.

## Retrying moves to the left status dot

Under badge mode, retrying stops being the amber ring and becomes an amber LEFT dot. It is NOT a `tabDotClass` case (that would fire in ring mode too): `applyTabBadgeMode`, run from `appendTabAfterWidgets` AFTER both the before- and after-side widgets compose (so the left dot's slot is found wherever the dot sits, even dragged past the name), TOGGLES the slot's class to `.tab-dot retrying` and titles it ("retrying an API error on its own"): the ring comes off and the slot is re-inked in one synchronous pass, so no paint sees the amber missing. A `.tab-dot.retrying { background: var(--st-retrying-bg); visibility: visible }` rule joins the dot colours. `tabDotClass` is unchanged, so ring mode never shows the retrying dot. When the Status dot widget is OFF there is no slot to carry the amber, so the retrying ring is kept. The re-ink drops BOTH `none` and `idle` before adding `retrying` (under the "Grey dot when idle" option a none-state slot renders `.tab-dot idle`, and idle would otherwise dim the amber; PR 2023). This sits retrying beside working and awaiting as a run-state colour; the dot shows the tab's single run state, so working, awaitingBg and retrying never collide on it.

Decided (the user, 2026-09-21): the retrying RING stays in RING mode, byte-identical to today; the left-dot retrying appears only under BADGE mode. Ring mode is unchanged, so a ring-mode-unchanged pin guards that turning the badge off leaves the retrying amber ring and no retrying dot.

## Blocked is unchanged

Blocked keeps its red dashed ring (`ring-needs-you` on a `tab-blocked` tab) and its translucent red fill (`styles.css:555`) in BOTH modes. It is a hard run-state stop that outranks the other run states, so it is not a top-right dot and not a left-dot colour: the whole-tab red ring and fill are the loudest cue and stay. No re-gating is needed (the ring class stays on a blocked tab), which reverses the earlier note's plan to re-gate the fill.

## Colours and the contrast floors

Two colours move: the Needs-you magenta (`--st-needs-bg`) as the top-right dot, and the retrying amber (`--st-retrying-bg`) as the left dot, both in both themes, reusing the existing tokens.

The Needs-you dot is a FILLED magenta dot on a ground it did not sit on before (the tab face). The retrying dot is a HOLLOW amber ring (transparent fill, an inset amber stroke), a distinct SHAPE (2026-09-23): its amber cannot reach the categorical deficiency floor against the filled working (gold) and awaiting (green) dots in the same left slot (dark retrying vs awaiting 2.7 deutan, light retrying vs working 3.3), so FORM, not colour alone, tells it from them, the way Blocked's dashed ring does. Pin both with the Needs-you arc's validator in `ui/webview/theme-parity.test.ts`: `deltaE` (OKLab x100), `cvdWorst` (protan and deutan, the worse), WCAG `contrast`. The rule: a dot pair whose hues clear the floors (deltaE at least 15 full colour, at least 8 under a deficiency) needs no shape; a pair whose hues cannot must wear a distinct shape, recorded at a drift-guard floor with the reason. WCAG 3:1 holds for each dot (the ring's amber, the magenta) on the tab face, hovered and selected grounds, both themes. The one pair no shape separates, the working GOLD against the awaiting GREEN (both filled, dark 4.2 protan), is a PRE-EXISTING miss conceded on the user's decision, recorded, not fixed here (the light pair clears, 21.2 full colour / 13.7 under a deficiency). The six left-slot classes (working, awaiting, retrying, unknown, idle, opening) are all covered in the test, retrying sharing the hollow form with unknown.

## The phone switcher

The same split holds on the phone. Under badge mode: Needs you becomes a magenta count dot on the current-session chip (`#mcur`) and each row (`.mrow`), replacing `#mcur.ask`'s dashed border and `.mrow.ask`'s magenta left bar (cited by selector). The phone dot RESERVES room rather than stacking (a static flex item, with `order: 1` on the chevron `.cv` and the close `.mclose` so they stay at the right edge and a wide count never covers them); it carries the count and a `role="img"` aria-label (PR 2023). Retrying becomes a HOLLOW amber leading dot on the phone too (`#mcur .wd.retrying` / `.mrow .workdot.retrying`: transparent fill, an inset amber stroke, the desktop's shape cue mirrored), so form not colour alone tells it from the filled working gold and awaiting green leading dots (the phone derives its retrying bit from the desktop `.tab-dot.retrying`). Blocked is unchanged. The leading gold/green working/await dot stays. The phone CSS and JS live in the kernel's mobile strings, so this is drawn there, not in the webview tab renderer. The phone's Needs-you dot carries the count in the same style chosen for the desktop.

## The setting

A per-browser boolean `tabStateBadge`, default ON since 2026-09-23, a checkbox in the gear's Tab strip section beside the tab lock (the row id `rs-statebadge`), following the tab lock's pattern: the `tabStateBadge` field on `RompSettings`, its entry in `DEFAULT_SETTINGS` (now true) and the read in `loadSettings`. The MECHANISM of the flip is the default itself: `DEFAULT_SETTINGS.tabStateBadge` is true, which the spread supplies whenever the key is absent, so a browser that never chose reads on. The read `s.tabStateBadge !== false` is only the GUARD around it, keeping a stored literal false as a chosen off and coercing a non-boolean stored value to a real boolean on (its one effect the default spread does not already cover). The EXISTING key is kept (absent means on, a literal false is a chosen off and stays off): no writer ever merged the old default into stored profiles (the gear's `load()` defaults exclude the key, no webview `saveSettings` caller, `broadcastSettings` and `installSettingsSync` write the stored object as-is, and feed.ts `setViewPref` is a raw read-modify-write of its own feed keys that never touches the whole object), so a stored false is always a chosen off and a fresh key would only discard it. Per browser, fanned out by settingsSync (`gear.js` save, the host repost `broadcastSettings` in extension.ts, receive `installSettingsSync` in settings.ts). The gear's preview (`gear.js` `demoTab` and `paintWidgets`, the ring section's demo) shows the Needs-you top-right dot and the retrying left amber dot when the switch is on, the ring when off, by running `applyTabBadgeMode` over each ring row's demo status (test 5 pins it). Flipping repaints in place, no reload (the settings event re-renders the strip). The switch changes only the Needs-you and retrying shapes; the dashed ring stays available (badge off is the pre-2026-09-23 behaviour), and Blocked is the same either way. The retrying LEFT dot is a HOLLOW amber ring, not a filled disc: a distinct SHAPE, not colour alone, tells it from the filled working and awaiting dots, because the amber cannot reach the categorical deficiency floor against them (the review: dark retrying-vs-awaiting 2.7 deutan, light retrying-vs-working 3.3). The Needs-you demo carries a count of 2 so the preview draws the numbered dot, and the demo composes both widget sides so a dot dragged past the name is re-inked as the strip does.
